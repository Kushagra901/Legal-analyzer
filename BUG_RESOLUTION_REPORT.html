MED-01: Production Connection Pooling on SQLAlchemy Engine VERIFIED
  • Architecture Label: DATA-DB-003-CONNECTION-POOLING
  • Target Files: backend/app/core/database.py, backend/tests/test_database_pooling.py

Problem: The SQLAlchemy engine was created with default unconfigured pooling, allocating only 5 connections without a recycle interval or pre-ping liveness test. High concurrency and idle periods led to dropped connections and pool exhaustion.

Solution: Configured driver-adaptive connection pooling with pool_size=10 (PostgreSQL) / 5 (SQLite), max_overflow=20 / 10, pool_pre_ping=True (proactive dead connection validation), and pool_recycle=1800 (30-minute recycling).

is_sqlite = settings.DATABASE_URL.startswith("sqlite")
connect_args = {"check_same_thread": False} if is_sqlite else {}

engine = create_engine(
    settings.DATABASE_URL,
    connect_args=connect_args,
    pool_size=10 if not is_sqlite else 5,
    max_overflow=20 if not is_sqlite else 10,
    pool_pre_ping=True,
    pool_recycle=1800,
)

Verification: 4 unit tests in tests/test_database_pooling.py passed.

MED-02: Application Structured Logging & Print Elimination VERIFIED
  • Architecture Label: OBS-LOG-001-STRUCTURED-LOGGING
  • Target Files: backend/app/main.py, backend/app/core/logging.py, backend/app/workers/tasks.py, backend/app/services/storage_service.py, backend/app/services/ocr_service.py, backend/tests/test_logging.py

Problem: setup_logging() was never called in main.py, and background tasks/services used unformatted print() statements, preventing Sentry ingestion and structured log parsing.

Solution: Implemented JSONLogFormatter for production environments, invoked setup_logging() before FastAPI creation, and replaced all raw print() calls with structured logging. Enforced confidentiality by logging only document_id references, never raw contract text.

class JSONLogFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        log_data = {
            "timestamp": datetime.now(timezone.utc).isoformat(),
            "level": record.levelname,
            "name": record.name,
            "message": record.getMessage(),
            "module": record.module,
            "line": record.lineno,
        }
        if record.exc_info:
            log_data["exception"] = self.formatException(record.exc_info)
        return json.dumps(log_data)

Verification: 5 unit tests in tests/test_logging.py passed, including an AST scanner confirming 0 print calls in backend/app/.

MED-03: Limit/Offset Pagination on List Endpoints VERIFIED
  • Architecture Label: API-REST-001-PAGINATION
  • Target Files: backend/app/models/schemas.py, backend/app/api/v1/routers/documents/crud.py, backend/app/api/v1/routers/admin.py, frontend/lib/api/client.ts, frontend/app/(dashboard)/dashboard/page.tsx, backend/tests/test_pagination.py

Problem: GET /api/v1/documents and GET /api/v1/admin/audit-logs returned unbounded database arrays, posing severe performance and memory risks under heavy volume.

Solution: Added Pydantic envelope models PaginatedDocumentList and PaginatedAuditLogList with items, total, limit, and offset. Added query parameters with validation (limit max 100, default 50; offset min 0, default 0). Updated TypeScript client and frontend dashboards to consume paginated items.

@router.get("", response_model=PaginatedDocumentList)
def list_documents(
    limit: int = Query(default=50, ge=1, le=100),
    offset: int = Query(default=0, ge=0),
    current_user: User = Depends(get_current_user),
    db: Session = Depends(get_db),
) -> PaginatedDocumentList:
    base = db.query(Document).filter(Document.user_id == current_user.id)
    return PaginatedDocumentList(
        items=[DocumentListItemResponse.model_validate(d) for d in base.offset(offset).limit(limit).all()],
        total=base.count(),
        limit=limit,
        offset=offset,
    )

Verification: 6 unit tests in tests/test_pagination.py passed; npx tsc --noEmit passed with 0 errors.

MED-04: Elimination of N+1 Query Anti-Pattern in get_document VERIFIED
  • Architecture Label: PERF-DB-001-RELATIONSHIP-EAGER-LOAD
  • Target Files: backend/app/models/database_models.py, backend/app/api/v1/routers/documents/crud.py, backend/tests/test_eager_loading.py

Problem: In get_document, all clauses were queried first, and then in a Python loop, individual SQL queries were issued for each clause's risk flags. A 60-clause contract caused 61 queries.

Solution: Established ORM bidirectional relationships (Clause.risk_flags and RiskFlag.clause) with selectin lazy loading, and applied options(joinedload(Clause.risk_flags)) in get_document to read risk flags directly from memory.

# ORM Relationship in Clause:
risk_flags = relationship("RiskFlag", back_populates="clause", cascade="all, delete-orphan", lazy="selectin")

# Eager-loaded query in get_document:
clauses_db = (
    db.query(Clause)
    .options(joinedload(Clause.risk_flags))
    .filter(Clause.document_id == document_id)
    .order_by(Clause.clause_number.asc())
    .all()
)

Verification: 3 unit tests in tests/test_eager_loading.py passed, verifying 0 additional SQL queries across 10 clauses using SQLAlchemy cursor execution listeners.

MED-05: Database Indexes on Foreign Key and Filtering Columns VERIFIED
  • Architecture Label: DATA-DB-004-INDEX-OPTIMIZATION
  • Target Files: backend/app/models/database_models.py, backend/alembic/versions/791aa19f3d22_add_foreign_key_indexes.py, backend/tests/test_model_indexes.py

Problem: High-cardinality foreign keys and filter columns lacked B-tree indexes, forcing sequential full table scans during document clause resolution, audit log queries, and chat lookups.

Solution: Added index=True across 14 relational columns in database_models.py and generated Alembic migration 791aa19f3d22_add_foreign_key_indexes.py.
